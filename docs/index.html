About the Build

The integration platform behind the simulation.

BankGate is a MuleSoft-based banking API integration platform built around API-led architecture. This simulator provides an interactive way to understand how banking operations travel through the Experience, Process and System API layers, while the actual integration implementation is available in the GitHub repository.

What is BankGate?

BankGate API Integration Platform

BankGate is a banking API integration platform designed around MuleSoft's API-led connectivity architecture. It separates consumer-facing APIs, business process orchestration and backend system integration into distinct Experience, Process and System API layers.

Talking points

Questions this project is built to answer

Why API-led connectivity instead of point-to-point integration?

Point-to-point integration means every consumer talks directly to every backend system, so the number of connections grows with every new app or system added. API-led connectivity splits that into three reusable layers — Experience (consumer-facing), Process (orchestration) and System (backend integration) — so a new client can reuse the same Process and System APIs instead of a new integration being built from scratch each time.

How does OAuth 2.0 work in this implementation?

Every Experience API endpoint sits behind OAuth 2.0 token validation before a request is allowed to continue. If the token is missing or invalid, the request is rejected with a 401 at the Experience layer and never reaches Process or System — the simulator's OAuth step shows exactly this checkpoint.

What happens when a duplicate customer is submitted?

The request is allowed to travel through OAuth and into the Process/System layers, where the duplicate check runs against PostgreSQL. On a match, System API returns a 409 Conflict (BANK-4091) and the request stops there — it does not re-attempt an insert. The simulator's Customers screen reproduces this path so you can trigger it directly.

Why split Experience, Process and System into separate Mule applications?

Each tier has a different reason to change: Experience changes when a client-facing contract changes, Process changes when business rules change, System changes when the underlying database or backend system changes. Deploying them as four separate Mule apps (Experience :8080, Process :8082, System :8081, Auth :8084) means one tier can be updated and redeployed without touching the others.

What does the System API actually own?

System API is the only tier with a direct PostgreSQL connection. It owns the `banking` schema — customers, accounts, kyc_verifications and transactions — including the foreign key and check constraints, which are also enforced at the API layer as a second line of validation.

How is rate limiting enforced, and what happens when it's exceeded?

A rate limiting policy is applied through Anypoint API Manager on top of the published BankGate API. Once the configured threshold is exceeded, the request is rejected at the API Manager layer with a 429 before it reaches Process, System or PostgreSQL — the Rate Limiting screen lets you trigger this by submitting requests rapidly.

Is this a real, deployed banking system?

No. BankGate is a real MuleSoft API integration platform — the four Mule applications, RAML contract, OAuth policy, MUnit suite and PostgreSQL schema all exist and are in the GitHub repository. This browser simulator is a visual re-creation of that architecture for demonstration purposes; it does not call the deployed Mule applications live.
